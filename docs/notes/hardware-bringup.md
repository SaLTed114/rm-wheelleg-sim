# 实车分阶段验证路线

本文记录未来拿到实车后的最小 bring-up 顺序。它是一组逐级验收门槛，
不是要在正式 controller 中增加同样数量的运行模式。

## 基本原则

- 嵌入式项目直接复用本仓库的纯 C control core，不重新实现另一份控制器。
- 每一级只开放完成验证所需的最小能量和功能；当前一级没有证据通过时，不进入下一级。
- 单项隔离由独立 bring-up 程序或测试任务完成，不向正式 operator command 和状态机加入通用 bypass 开关。
- 硬件层始终保留独立于 controller 的最终失能、超时归零和力矩限制。
- 每一级保存原始反馈、snapshot、最终输出和异常记录，必要时可在 PC 上离线重放。

## 验证阶段

1. **目标平台与数值**：编译纯 C core，核对数据类型、控制周期、数学函数和固定输入输出，确认 PC/MCU 数值近似一致。
2. **只读传感器**：执行器强制为零，逐项核对 IMU、轮、关节和云台反馈的单位、方向、零点、频率、时间戳与超时。
3. **执行器映射**：车体可靠固定，以很小的独立正负指令确认六路执行器顺序、方向、力矩到电流换算、限幅和急停。
4. **腿部链路**：轮输出关闭，先验证腿运动学，再以低输出限制单独验证腿长/腿角 PD；不运行 LQR。
5. **观测器**：通过人工推动、低速拖行和数据重放验证姿态、腿状态、`S/DS`、`PSI/DPSI`、融合状态及异常测量处理。
6. **状态机与安全**：验证上电 OFF、restart、起身、失能、通信超时、电机掉线和异常恢复，暂不追求运动性能。
7. **受保护静态平衡**：使用支架或吊绳，先限制输出完成起身和原地平衡，再逐步开放正常力矩和小扰动恢复。
8. **普通运动**：依次验证低速纵向、停车锁位、低速云台跟随和 front/rear 切换；偏航先以 `scale=0` 核对反馈路径，再启用默认 `0.9` 加速度前馈。
9. **性能与任务**：最后扩展高速移动、移动转弯、roll 补偿、SPIN、扰动恢复和性能边界。

## 隔离方式

部署阶段只需要三种隔离边界：

- **数据边界**：硬件 adapter 将带时间与有效性的原始设备数据整理为 `bc_sensor_feedback_t`。
- **算法边界**：独立 bring-up 程序按需调用运动学、observer、PD 或 controller；正式控制循环仍只走 controller facade。
- **能量边界**：controller 输出之后、真实电机之前设置硬件相关的 enable、超时、限流和急停门控。

除非实际 bring-up 证明上述边界不足，不预先设计通用 debug command、任意模块旁路或大量编译期开关。
